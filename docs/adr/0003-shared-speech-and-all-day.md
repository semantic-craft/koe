# 共享语音识别与全天记录

## 问题

设置曾把本机识别和音频上传许可混为一个开关，领夹模式没有解释采集与听写的关系。旧全天监听随 Flutter 宿主移除，当前原生流程没有等价入口。外部输入法需要复用已识别文字，不能为同一段声音启动第二套识别管线。

## 决策

`SpeechSession` 由 Rust Runtime 拥有，绑定记录、请求、识别引擎和结果归属。Mac 麦克风与 D3200 实时输入，以及 Apple / 下载模型的文件转写，共同使用这条识别路径。云端文件转写保留既有批处理任务，结果同样经 Runtime 校验请求身份并持久化。Apple 识别通过已有平台 effect 接口执行；下载模型在 provider 工作线程内加载和推理，结果直接返回 Rust。Swift 只呈现快照并执行平台采集，不保存另一份业务状态。

下载模型参考 [Hex 的固定版本实现](https://github.com/anomalyco/hex/tree/4793e168f4958c7c31aa924a8fe027768c7fcc51/src/transcription)。目录使用固定模型身份、文件大小和 SHA-256。下载先写临时文件，验证后原子发布，再实际加载。模型文件存在不能代表识别可用。推理依赖锁定 `transcribe.cpp` 源码，静态链接 CPU 后端，不通过 shell、HTTP 转发服务或外部可执行程序粘接本机识别。

全天采集持续运行，按有界片段产生普通 `ProductRecord`，片段以全天会话身份关联。当前片段接收新声音；已封口片段完成识别后进入既有整理流程。复用普通记录的原文、来源引用、审核、保存和重试语义，不再创建第二套持久化“识别窗口”状态机。

这项选择避免持续修改同一条记录时使在途纪要的 `input_revision` 失效。纪要针对稳定原文生成，下一段继续录音。

听写是全天听记之上的显式选择范围。开始和结束听写不会关闭全天采集。只有确定文字完成工作区提交后，Runtime 才向本地桥发布可供外部输入法消费的文字；全天背景内容不能自动成为输入法提交。外部输入法负责润色与插入。原有 PCM 订阅独立保留。

识别引擎、音频上传许可和文字整理服务分别配置。本机引擎失败不自动上传音频。本机 HTTP loopback 文字服务允许无密钥配置；远端服务继续使用现有凭据规则。

## 比较过的方案

独立持久化识别窗口会与记录的请求、处理状态和恢复规则重复，因此不采用。一个全天巨型记录会持续改变原文版本，也不采用。共享识别会话加普通分段记录同时保留单一所有权和稳定的分析输入。

## 验收标准

标准参考 [Google 代码评审指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html) 的设计、真实功能、复杂度和测试要求，并落实为本仓库可验证的行为。

- 首次下载必须经过校验和真实加载，取消或失败不能显示已就绪。
- 同一段真实测试音频通过实际模型产生文字，保存后重新打开仍保持一致。
- 迟到识别结果不能写入已取消的请求或其他记录。
- 全天分段不停止采集，已完成片段与进行中片段的保存和整理互不冒充完成。
- 听写范围外的文字不作为输入法提交；先保存，后发布。
- 界面可找到配置、开始、结束、重试和说明；演示明确标注示意。
- 回归测试在旧实现失败，修改后通过。模型实测、自动化测试和真实硬件长时间验收分别报告。

旧版迁移入口和专属导入流程被删除，已保存的数据与当前工作区读取继续保留。
