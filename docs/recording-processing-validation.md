## 当前连接策略

手动断开状态随已绑定设备保存，重启 App 后仍保持离线。打开扫描窗口只发现设备；点选设备连接后才清除该状态并恢复正常的掉线重连。手动断开期间，快捷录音提示先在应用内连接，不隐式抢回设备。旧版本没有此字段的记录保留原有自动连接行为。以下“会话内断开”的验收记录属于先前版本。

状态写入串行执行并通过临时文件替换，避免并发设备信息更新覆盖新意图；断开操作在释放蓝牙前等待保存。`test/recording_shortcut_test.dart` 使用真实临时目录保存、重新加载并创建控制器，覆盖重启、扫描、快捷录音、显式连接恢复、旧格式与写入顺序。

## 本轮行为

- 点击尚未配置的云端引擎，直接打开配置窗口。保存不会切换当前引擎，关闭窗口后点击卡片启用。Qwen/豆包表单按引擎建立独立状态。
- 文件任务写入应用文档目录 `AnkerRecorder/file_jobs.json`，保存录音标识、转写类型、配置版本、服务地址、模型、语言和任务阶段；不保存 API Key。恢复时按原服务取当前凭据，服务地址变化时停止执行。
- 排队任务重启后恢复；千问已经保存任务编号时直接查询，不重新上传或提交。上传/提交结果不明的任务显示需重试提示，不自动再次收费。
- 同步服务中断后保留任务和错误，使用录音详情的重试入口。已返回的文字先写入任务记录，再写转写库，完成两步后才标完成；重启可直接保存已有结果。
- 自动 BLE、手动 BLE 和已解密的 Wi-Fi 导出完成后共用处理入口；仅对已转换 WAV、已启用自动转写、已配置引擎且没有转写/已有任务的录音排队。重复完成通知不会再次提交。目录扫描、重命名不会批量触发收费。
- 删除录音同时丢弃任务；排队和执行中的录音限制重命名，其他任务随重命名更新路径。任务记录损坏时停止提交，不当作空队列覆盖。

## 2026-10-15 真机千问验收

基线 `67144e6` 安装到 Hermes iPhone 与本机 Mac 后，千问上传在两端共用的 Dart 服务中复现 HTTP 400 `MalformedPOSTRequest`。同一 WAV 用独立编码器上传成功；仅交换文件 part 的 `Content-Disposition` / `Content-Type` 顺序也成功。修复使用 `OssUploadRequest`，先写 disposition，再写 type，保留流式文件与进度回调。原 `http.MultipartRequest` 在此 OSS 接口不兼容；不是 Key 失效或模型选型问题。

- 回归：原真实服务调用在修复前上传失败，修复后上传、提交、查询与读取结果成功。`test/qwen_stt_test.dart` 检查实际序列化的文件头顺序、长度和音频字节；先红后绿。270 项测试通过，`flutter analyze --no-pub` 无问题，iOS/macOS Release 构建成功。
- 安装：修复版已覆盖安装到 iPhone `com.semanticcraft.soundcore` 和 `/Applications/Soundcore Manager.app`，保留数据。两端使用已有千问 Key 与默认 `qwen-audio-3.1-asr-flash-filetrans`，未变更正式模型方案、分析方案或同步方案。
- 样本：用户用录音豆独立录制约 30 秒测试音频，iPhone 通过 BLE 取回，保留设备原件。此前自动处理走 Apple；本轮显式重新转写走千问。
- iPhone：云端任务编号保存且状态为 running 后 SIGKILL App；重启后同一编号变为 complete，界面显示新千问文字（131 字）。恢复记录位于本机忽略目录 `build/device-validation/ios-interruption.json` 与 `ios-restored.json`。
- Mac：使用从 iPhone 取回的相同 WAV（本地测试传入，不是同步功能）。App 内启动千问转写，保存任务编号后 SIGKILL；重启后同一编号 complete，界面显示文字（129 字）。证据为 `mac-interruption.json` 与 `mac-restored.json`。两端分别提交各自验收任务，不能据此推断跨端去重。
- 结果：这段样本中千问识别出了“千问”和“DeepSeek”，但两次输出有细微差别；尚无人工逐字标注，不给准确率或优于其他模型的结论。
- 边界：进程被结束后由用户/测试重新启动才恢复；本轮没有验证锁屏持续执行、系统休眠、上传/提交编号尚未保存时的恢复。Mac 扫描未找到录音豆，未证明 Mac 直接 BLE 取回。iPhone 明确断开连接后再次扫描仍未发现，故不能把原因只归于手机占用。没有解绑或删除录音。
- 已知偏差：验收时出现另一条约 14 秒录音，保持原样，其旧失败记录未作为本轮样本重提。自动传输开关重启后的保持行为需另查；本轮曾关闭但后续取回了新增录音。

## 2026-10-15 Mac 蓝牙发现与直接取回复验

上一节的“手机明确断开”只是瞬时 UI 状态；继续观察发现它随即自动重连。根因是 `BleService.disconnect()` 清理后重复发出断开通知，控制器在第一条通知后清除手动断开标记，第二条便启动自动连接。

- 修复：一次手动断开只发一条通知；控制器的手动断开意图保持到本会话显式扫描/连接，并拦截重复通知、迟到扫描结果和重连计时器。异常掉线仍自动重连。
- 回归：`manual disconnect survives duplicate notifications and stale scans` 修复前失败（预期扫描 0 次，实际 1 次），修复后通过；异常掉线另有正向用例。272 项测试通过，静态分析无问题，iOS/macOS Release 构建并覆盖安装成功。
- 硬件对照：调用实际 BleService 的同一个 12 秒扫描程序，手机占用时扫描到 39 个其他外设、D3200 为 0，退出码 2；修复后手机断开，同程序扫描到 47 个外设、D3200 为 1，退出码 0。手机在约 40 秒后的观察中仍离线。日志为本机 `build/device-validation/ble-phone-connected.log` 与 `ble-after-disconnect-fix.log`。没有解绑、重置或切换系统蓝牙。
- 正式 Mac App 发现并连接 D3200，读取固件 04.92、电量和录音列表。先将此前从 iPhone 复制的 WAV 移出导出目录保留，再对 16:25 样本点击“下载录音”；界面从下载进度进入“已下载”，本地列表新增 1 条并出现播放器。另一条 14 秒录音与设备原件均保留。
- 新下载 WAV 为 2,905,004 字节、48 kHz 单声道 16-bit、30.26 秒，与 iPhone 样本参数和帧数相同。两个平台解码后的 WAV SHA-256 不同；逐样本最大差值 4、RMS 差值 0.439（16-bit PCM 单位），因此不宣称逐字节一致或人工听辨完成。核对结果在本机 `mac-ble-download.json`。
- 原有千问转写仍显示；本次重取同一录音不重复提交转写。双端千问提交与同任务编号恢复证据沿用上一节，不将此次下载当作新的云端处理验收。
- 会话边界：手动断开意图不跨进程保存，重开 App 仍按已绑定设备自动连接。切换到另一端时，在当前连接端点“断开连接”，保持其进程，然后在目标端扫描连接。本轮未实现跨端同步或连接仲裁。
