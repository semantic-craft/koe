# Koe 资料包格式（`.koepack`）

资料详情「更多 → 导出…」生成，「新记录 → 导入资料包」恢复（#145）。一个包只装一条资料。代码在 [crates/koe-engine/src/cicada.rs](../crates/koe-engine/src/cicada.rs)（`KOEPACK1\n` 帧格式、SHA-256 校验、导出与导入去重）及 [crates/koe-client-core/src/lib.rs](../crates/koe-client-core/src/lib.rs)（客户端重导出）。

## 两种导出

| | 阅读稿（`.md`） | 可恢复资料包（`.koepack`） |
| --- | --- | --- |
| 给谁 | 人读、粘贴到别处 | 另一台设备、重装后的 Koe |
| 内容 | 标题、时间、地点、主题、带时码和发言人姓名的正文、书签 | 下文全部字段 |
| 原音频 | 从不包含 | 用户打开「包含原音频」才包含，默认不含 |
| 能否导入 | 不能 | 能 |

## 文件结构

```
KOEPACK1\n
<说明的字节数，十进制>\n
<说明：UTF-8 JSON>
<原音频的原始字节，仅在 audio.included = true 时存在>
```

不压缩、不分块；原音频按原件字节原样放在说明之后，导出和导入都按块流式读写，不把整段音频读进内存。导出先写 `<名字>.koepack.part`，写完才改名，取消或失败时删除，不会留下看似完成的文件。

## 说明（manifest）字段

```jsonc
{
  "format": "koe-material-pack",
  "version": 2, // 有纪要时为2；无纪要继续输出1
  "exportedAt": "2026-10-19T10:00:00.000",
  "material": {
    "contentHash": "<原音频 SHA-256，64 位小写十六进制>", // 资料身份
    "title": "周会",
    "source": "device | localImport | phone",
    "deviceFileId": 1792377669,        // 只有录音豆录音有
    "recordedAt": "2026-10-12T09:30:00.000",
    "place": {"label": "杭州市西湖区", "source": "manual", "capturedAt": "…"},
    "audioExtension": ".wav"
  },
  "transcript": {
    "text": "<转写服务原文>",
    "manual": "<用户校订后的正文，没改过就没有>",
    "segments": [{"text": "…", "startMs": 0, "endMs": 4000, "speaker": "1"}],
    "segmentSpeakers": {"2": "2"},     // 片段序号 → 改正后的发言人
    "speakerAliases": {"1": "王老师"}, // 发言人 → 用户起的名字
    "provider": "qwen", "sourceLanguage": "zh", "revision": 2,
    "translation": { /* 与 transcripts.json 中的译文同构 */ }
  },
  "minutes": {
    "current": { /* 下文白名单 AnalysisResult */ },
    "history": [ /* 最近最多10版 */ ]
  },
  "bookmarks": [ /* RecordingBookmark 去掉 recordingKey */ ],
  "topic": {"title": "年度预算", "kind": "general"},
  "audio": {"included": true, "extension": ".wav", "bytes": 8044, "sha256": "<同 contentHash>"}
  // 或 "audio": {"included": false}
}
```

**刻意不写入：** 任何文件路径（本机或原导入来源的 `originalPath`）、本机 recording key（`path:…` / `file:…`）、API Key、录音豆配对或加密信息、Mac 归档配对。重装后容器路径会变（PR #239），所以资料身份只用内容摘要和录音豆文件号。

## 导入规则

1. **校验先于写入。** 魔数、说明长度、JSON、必填字段、原音频字节数和 SHA-256 任何一项不符，都直接报「资料包已损坏 / 不完整：…」，资料库、文件和书签都不改动。来自更高版本格式的包提示先更新 App。
2. **找同一份资料：** `deviceFileId` 只用于找候选，须核对实际音频 SHA-256；不能仅因文件号相同就合并。再按 `contentHash` 找资料库原件。都没有且包里有原音频时，走普通的「导入本地音频」保存原件（同内容复用、不记录来源路径），再恢复其余内容。已登记同摘要但原件缺失时，从包内已校验音频补回原路径，不另建资料；已有不同内容的原件绝不覆盖。
3. **只补缺，不覆盖：**
   - 本机没有正文：恢复原文、校订、片段时码、发言人改正、发言人姓名、译文。
   - 本机正文与包相同：只补本机没有的发言人姓名和译文。
   - 本机正文不同（同身份不同手改版本）：本机正文不动，包里的正文放进「待比较版本」，详情页提示「导入的资料包带来另一个版本的正文」，用户自己选择采用或保留。
   - 书签：位置、备注、原句都相同的跳过；id 已被占用的换新 id，不替换本机书签。
   - 地点：本机没有才补。主题：本机未归类（或待归类）时放进同名主题，没有同名主题就新建。
   - 纪要：本机没有当前纪要时采用包内当前版；已有当前版永不自动覆盖，不同包内当前版进入既有版本历史。来源快照和 sourceHash 原样保留；与本机正文不一致的纪要标过期，不能按旧时码回听。
4. **重复导入：** 第二次导入同一个包什么都不新增，提示「这份资料已在资料库中，未重复导入」。导入不排队转写或整理任务。
5. **包里没有原音频、本机也没有这条资料：** 作为文字资料导入（资料 → 文字资料），注明缺原音频和书签回听；正文与时码可读。「补配原音频」时必须是同一份原音频（SHA-256 一致），配上后按第 3 条完整恢复到这条录音，文字资料记录随之移除。再次导入同一个包不会再建第二条文字资料。包内纪要及历史保存在这条文字资料已有的 restore manifest 中，可只读查看；不同纪要保留为候选，不覆盖当前文字或纪要。没有完整逐字稿但有纪要时，只显示明确标注的“纪要原文快照”，不伪造逐字稿或可靠时码。补配成功后才迁入录音的纪要槽并删除文字占位；恢复失败保留占位以便重试。

## 纪要白名单与冲突

每份当前/历史纪要只携带 `text`、`sourceHash`、`model`、`instruction`、`sources`、`createdAt`、可选 `editedAt`/`templateId`、`templateVersion`、`isDraft`。`text` 是完整结构化纪要，包含议题、术语与采纳凭证。类型、时间、版本、嵌套引用及实际原文识别写法均先校验；未知纪要格式拒绝整个导入。派生 fingerprint 在目标端计算，本机分析 key、缓存、任务和凭据不进入包。用户自己写进正文的路径不属于元数据清洗范围。

包内最多10版历史；目标录音沿用现有最多30版历史，无音频文字占位最多10版。导入时按完整白名单内容去重（纪要 JSON 对象键顺序不影响身份），再按修改/生成时间及规范内容稳定排序截取。不同的包内当前版保留最后一个历史槽，其余槽留给最新候选；重复导入不会循环挤换已裁掉的旧版本。本机当前版始终保持，用户可用已有版本历史入口比较或恢复。历史达到上限后，旧采纳凭证对应的快照可能不再保留，界面如实说明。

纪要槽的用户写入持有可撤销的所有权 token；同一存储的变更、结果发布、保存及失败回滚串行完成，普通保存也在轮到执行时才抓取快照，避免另一槽把失败的暂存结果持久化。导入跨越音频、正文、书签和纪要多个存储，不承诺跨文件原子事务；后续 I/O 失败会报未完成，可能已有部分内容落盘，重试依靠去重补齐，不显示“现有资料未改动”。

## 版本演进

文件 framing 仍为 `KOEPACK1`。无纪要的包写 manifest version 1，携带纪要写 version 2，避免旧 App 静默忽略纪要。新版读整数1/2；版本1夹带 minutes、非正整数或未来版本均拒绝。读写两端都限制 manifest 为32 MiB；超限导出失败，不留下看似完成的包。

原音频补缺使用原子落盘与内容哈希校验，目标已存在时失败而不覆盖。
