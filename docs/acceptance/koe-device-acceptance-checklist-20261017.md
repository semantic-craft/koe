# Koe 真机验收执行清单（2026-10-17）

本清单把 #15、#16、#71、#95、#96、#97 与 #92 的真机项按依赖顺序合并成一次可执行验收。代码工单关闭、自动化测试、截图和构建成功都不替代这里的真实操作。

工单入口：[#15](https://github.com/semantic-craft/koe/issues/15)、[#16](https://github.com/semantic-craft/koe/issues/16)、[#71](https://github.com/semantic-craft/koe/issues/71)、[#95](https://github.com/semantic-craft/koe/issues/95)、[#96](https://github.com/semantic-craft/koe/issues/96)、[#97](https://github.com/semantic-craft/koe/issues/97)、[#92](https://github.com/semantic-craft/koe/issues/92)。

清单编写时功能基线 `ab5dcdc`（PR #98），`main@f49e22e`（PR #99 文档合并）；以实际安装构建记录为准。

## 执行规则

- 全程使用同一个最终安装构建；每次重装或换构建都要重新记录构建身份。
- 只记录脱敏证据：设备型号、App 构建、时间、文件大小/时长、UI 文案、截图和本地只读元数据；不上传私人音频、完整转写、Key 或内部 ID。
- 真实模型调用由你决定是否付费；记录调用次数和账单，避免重复提交。
- 每项只记 `PASS`、`FAIL`、`BLOCKED` 或 `UNCOVERED`；未执行不能算通过，部分成功不能写成 PASS。
- 失败时记录可复现步骤和脱敏后的提示；不要为了继续验收而删除原始录音或清空数据。
- 自动控制服务故障只记工具问题，不直接判业务失败；换一种人工操作继续。

## 1. #15 iPhone 核心验收

### 1.1 配置、录音与回听

- 从无模型配置开始，只用 UI 完成设置并启用一个模型；记录保存、清除、重启后的配置状态。
- 录音豆独立录音一次；App 发起录音一次。两次都完成取回、完整回听、真实转写和结果保留。
- 从列表打开详情，确认播放进度从 0 到结尾完整推进；转写文字与回听内容一致。
- 生成一次摘要或分析，确认阅读、复制和分享入口可用。
- 记录启动到可用、连接到开始录音、列表/详情打开的实际耗时。

**证据：** 构建与设备信息、配置保存/清除/重启后的设置截图、两条录音的取回与状态截图、播放进度和结束时间、转写文字与回听一致性的记录、摘要/分享入口截图、启动/连接/打开耗时。

**通过条件：** 两条录音链路都能完成取回、回听和真实转写；配置重启后不丢；结果可阅读和分享；没有依赖飞书 App。

### 1.2 中断、切后台、锁屏与重启

- 录音或取回过程中切到后台、锁屏、短暂断开蓝牙/网络，再恢复；记录 UI 是继续、明确重试还是明确失败。
- 杀后台重启 App，确认本地录音条数、文字、状态、任务记录不丢；处理中任务能恢复或给出可执行的重试入口。
- 对同一录音重复刷新、重连，确认不产生重复条目或重复付费任务。

**证据：** 中断与恢复前后的状态截图、本地条数、任务记录（stage/taskId）、重试入口、重复刷新/重连后的条目数和付费任务数；重启前后的文字和状态对照。

**通过条件：** 状态文案可理解；录音不丢；任务可恢复或明确重试；重启前后没有重复提交。

### 1.3 主题与笔记基础

- 创建一个书籍主题（书名、作者）和一个普通主题，设置当前主题；取回一条短录音，确认自动归入。
- 跨日后确认当前主题清空；无当前主题的录音进入待归类。
- 对一条待归类录音查看推荐归类/偏离提示，确认在用户确认前不自动生成笔记。
- 两类主题各生成一次笔记；检查笔记能跳回原文、可编辑，重新生成前有覆盖确认；重启后不重复收费。
- 手动生成一次主题汇总，检查过期提示；把主题标为读完/归档后不再显示过期，重新打开可恢复。
- 确认会议录音、手动摘要、纪要和导图流程不受主题功能影响。

**证据：** 书籍/普通主题与当前主题截图、归入和待归类结果、推荐归类提示、两类笔记生成次数和模型调用记录、跳转原文/编辑/覆盖确认截图、汇总过期与归档前后截图、会议录音和摘要/纪要/导图回归截图。

**通过条件：** 主题归类、两类笔记、跳转/编辑/覆盖确认和汇总过期行为符合 #49 规格；会议流程无回归。导出与分享的细节在 #95 验收。

### 1.4 可访问性与日常体验

- 用大字号打开设置、录音列表、详情和确认弹窗，确认关键按钮不被截断。
- 用 VoiceOver 走一遍“连接 → 录音/取回 → 打开详情 → 播放/暂停 → 退出”的关键路径。
- 记录长录音处理时的电量、内存或明显发热/卡顿；记录空闲时是否有不必要的后台工作。

**证据：** 大字号下设置/列表/详情/确认弹窗截图、VoiceOver 操作录屏或逐步记录、长录音处理与空闲时的电量/内存/发热/卡顿记录。

**通过条件：** 关键流程在大字号和 VoiceOver 下可达；日常使用不需要进入诊断页；失败有可执行入口；用户本人认可“轻便好用”。

## 2. #71 取回后自动转写（A4/A5）

本项按 #13 的原真机清单拆分：A4 验证自动转写开关，A5 验证 BLE 自动/手动取回各一次且不重复。

### 2.1 A4：自动转写开关

- 开启自动转写，设备独立录一条短录音，重新连接并完整取回；确认自动进入转写且只提交一次。
- 关闭自动转写，再录一条并取回；确认只下载、不发起云端请求，详情仍保留手动转写入口。
- 在未配置模型时取回一条录音，确认能从详情进入可达的配置页；配置后手动重试成功。

**证据：** 录音前后本地/设备条数、任务记录（stage/taskId）、模型调用次数或账单、开关截图、失败提示截图。

**通过条件：** 开启时自动转写一次；关闭时零云端请求且手动入口可用；重复刷新/重连不重复提交；失败可恢复且原始音频保留。

### 2.2 A5：BLE 自动与手动取回

- 设备独立录音后重连，分别走一次 BLE 自动取回和一次手动取回；每条只转写一次。
- 重复刷新或再次重连，确认不重复创建任务，已有文字和状态不变。
- 取回前后核对设备端/本地条数，完整回听每条录音；记录文件是否完整取回。
- 如条件允许，在 BLE 取回接近结束时让设备离开范围：文件保留、提示“未完整取回”、不自动转写；重连后能重新拉取并正常转写一次。

**证据：** 取回前后条数、每条录音的回听起止时间、任务记录、UI 的完整/未完整提示、重复连接后的任务数量。

**通过条件：** 自动和手动两条路径都能完整取回且只转写一次；重复操作不重复提交；拦截的不完整文件不被自动转写，重连后可补取。

**未覆盖：** 真实 Wi-Fi SoftAP 硬件若本次不做，明确记 `UNCOVERED`，不写成已验证；它不替代 A4/A5 的 BLE 结论。

## 3. #96 恢复后最终转写不缩水

- 记录 iPhone、iOS、App 构建、语音服务与模型。
- 用一条 20–40 秒短录音开始实时转写，确认屏幕出现多句实时稿。
- 保持实时订阅时让录音停止、切后台或短暂断开，等待最终结果。
- 核对最终文本包含此前全部实时句子的语义，不是只剩末尾一句；回听音频核对内容。
- 杀后台重启，重新打开该录音，确认文本仍完整，且没有重复提交付费任务。
- 若出现缩水，只记录时间点、显示行数/字数、服务事件类型（done/error）和构建；不上传音频或完整转写。

**证据：** 构建与服务/模型信息、实时稿句数或字数、最终稿句数/字数、回听核对记录、重启前后文本对照、任务数量和账单、失败时的 done/error 事件与时间。

**通过条件：** 最终文本、持久化读取和回听三者一致；重启不改变文本；没有额外付费重试。失败可复现时另开修复 PR。

## 4. #92 同一文件时长元数据

先选一条会触发暂停续录或断连重连的短录音；如果旧 15:18/15:07 文件仍在本机，也可只读核对，但不要修改或移动它们。

### 4.1 重启前采集

- 记录 App 构建（版本 + commit、安装方式）、iPhone 型号/iOS、录音豆固件。
- 记录文件路径/fileId、文件名、字节数、修改时间。
- 记录 WAV 头：`sampleRate`、`channels`、`bitsPerSample`、`byteRate`、声明数据长度、RIFF/data chunk 数量。
- 记录本机只读解码时长（`afinfo`/`ffprobe` 等）和实际回听时长。
- 记录 UI 列表/详情显示时长，以及此前是否发生暂停续录或断连重连。
- 若无法在不导出音频的前提下读取 WAV 头或解码时长，把该项记为 `UNCOVERED` 并说明原因；不要为了验收把音频上传到任何服务。

### 4.2 杀后台重启后采集

- 不修改文件，直接重启 App，重复记录同一路径/fileId 的字节数、修改时间和 WAV 头字段。
- 重复记录解码时长、回听时长和 UI 时长。
- 对照两次记录：字节数/声明长度是否变化；UI 时长是否变化；UI 是否与解码/回听一致。

### 4.3 判定规则

- 字节数和声明长度不变、只有 UI 变化：归显示/缓存问题，记录 App 构建和复现步骤。
- 字节数或声明长度增长：检查是否重复追加、是否有静音/重复片段，并比较解码时长和回听时长；不直接断言音频损坏。
- UI、解码和回听三者一致但数值偏大：记录为实际音频长度变化，继续核对录音操作和文件来源。
- 旧 15:18 `04:37→08:46`、15:07 `00:25→02:11` 只作为历史观察；没有同一文件前后证据时，不把缓存缺陷当作已证实根因。

**证据：** 同一路径/fileId 的重启前后两张记录表（字节数、修改时间、WAV 头字段、解码/回听/UI 时长）、App 构建与设备信息、操作是否含暂停续录/重连；可附截图或本机只读元数据文件，不上传音频或转写正文。

**通过条件：** 对相同且不变的音频，保存、重新加载和重启后时长一致；真实音频增长能正确反映；证据足以区分显示、元数据和音频内容。未满足时 #92 保持 OPEN，只记录已排除项和待采集项。

**证据：** 构建与 Qwen 配置、两个主题及至少 3 条录音/笔记的截图、两类汇总截图与来源跳转、编辑/覆盖确认/过期/归档截图、长主题续跑与重试的任务记录、调用次数和账单、会议与摘要/纪要/导图回归截图。

**通过条件：** 两类汇总内容与排序正确、来源可追溯；过期/归档/覆盖行为符合 #53；重启与重试不重复收费；其他流程无回归。
