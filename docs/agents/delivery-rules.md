# 交付、阻塞链与测试规则（完整原文）

> 2026-10-19 从 AGENTS.md 原样移入；此后与 AGENTS.md 同步维护，正文改动须两处同步。AGENTS.md 只保留精简版硬规则；两者冲突时以 AGENTS.md 为准并先修本文。

## 交付与验收（硬规则）

- 只经分支与 PR 交付，只用 squash 合并；不直接推 main，不用 merge commit，禁止 force push；中断的 agent 运行留下的 WIP 提交留在分支上，合并时 squash 掉。
- 每个 commit 正文和 PR 正文都要写清三项：①回退测试：哪条回归测试先失败、修后通过；没有就说明为什么。②真实使用情况：在真机、真实数据或真实界面上实际跑了什么、结果如何；没跑就写「未在真实环境验证」。③没跑到的项目：跳过的检查、没覆盖的场景和原因。只写「测试通过」不算验收，旧记录不能充当这次的证据；squash 合并时把这三项带进合并提交正文。
- 新教训先记进 [lessons.md](lessons.md)（出处、修复、Seen 计数），够分量的再补进 [CONTRIBUTING](../../CONTRIBUTING.md) 的十条规则；同一条教训在 3 个不同日子出现，就升为本节硬规则。
- **阻塞链。** 工单阻塞时先追到根因，清障或交给能处理的人。把 macOS、iOS、Android 的真机、实体 D3200 和签名安装验收拆成独立 `ready-for-human` 工单，代码过审后先合并。代码审查和签收证据见 [代码审查标准](code-review-standards.md)。


## 测试硬规则（2026-10-16 按用户要求去掉无收益测试）

- 只写改动前会失败、能拦住真实回归的行为测试；PR 里说明它在改动前怎样失败。
- 不加凑数、重复已有覆盖、或只测实现细节（内部常量、调用次数、复杂度、源码字符串）的测试；不加与风险不相称的性能基准、长时间压测或多轮循环。
- `## 本机待办` 和 `## 需要真机` 只列这次改动真正碰到、而 CI/已列的门禁覆盖不到的内容；一个命令已包含另一个时只列外层那一个。
- 花钱或丢数据的路径、只能在真机上验的项、安全扫描照常保留。
